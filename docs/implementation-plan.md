Python is the reference orchestration/analysis language. Critical emitters use each component's implementation language and do not depend on Python in interrupt/tick paths. ## IMU marker integration work package

The user-confirmed direction adds a configurable hardware acceleration-threshold interrupt as a diagnostic marker while keeping the continuous gameplay stream unchanged. Apply the [marker trace contract](trace-format.md#additional-imu-threshold-markers) and [shared design](https://github.com/motion-tennis/documentation/blob/main/docs/imu-trigger-markers.md) within these stage scopes:

1. **S1: offline contract conformance.** Extend the auditor with meaningful marker fixtures and checks before claiming marker analysis works. Cover wrong sessions, reboot, ambiguous capture timing, missing/duplicate links, several markers per transaction, dropped/failed targets, out-of-order records, missing stages and source loss. Preserve the supplied core tests; S0 establishes the contracts and explicitly scoped contract fixtures without claiming this broader audit coverage.
2. **S2: isolated hardware evidence.** With the controller component, characterize detector semantics, supported threshold/duration/filter settings and evaluation rate independently of raw sample ODR. Verify concurrent acquisition/IRQ delivery, early timestamp error, status clearing/latching, repeated triggers and haptic-induced motion. Record actual firmware/driver capabilities; reading samples alone does not establish IRQ support.
3. **S2 exports, S3 integration.** Add bounded `imu_threshold_trigger` and `trigger_link` evidence in the owning components. Preserve ESP32-local `t_trigger`, configuration version, session-scoped identity and explicit primary sample/transaction link. Keep unresolved evidence visible; never move a failed target to a later successful sample.
4. **S3 viewer, S4 four-player coverage.** Join the marker through pose, logical query, batch, decision, accepted commit, feedback and eligible cue identities. Marker metadata changes neither the gameplay schema nor 200 Hz schedule, priority or 50 ms expiry. Deliver the complete one-controller path and visible gaps at S3 before claiming the full four-player view.
5. **S3 measurements, S5 matched comparisons.** Publish separate ordinary sample, primary marker-response and explicitly linked semantic swing/cue populations. Count every outcome and report cutoffs, uncertainty and detector delay. Compare instrumentation enabled/disabled under matched workload at S5; collection never becomes a gameplay dependency.

Only the existing core offline auditor is implemented. Its acceptance of additional named stage records does not satisfy this work package or establish full-path marker tracing.

## Clock-mapping and uncertainty-viewer work package

The agreed design uses Pi-owned affine mappings with drift correction and visibly bounded debug timing. Follow the [metadata contract](trace-format.md#pi-reference-clock-metadata), [canonical clock mapping](https://github.com/motion-tennis/documentation/blob/main/docs/coordinates-and-time.md#pi-reference-clock-mapping) and [ADR 0009](https://github.com/motion-tennis/documentation/blob/main/docs/adr/0009-pi-reference-clock-mapping.md). This work does not change the gameplay protocol, profile rates or deadlines. S0 defines evidence/fixture expectations; S1 implements offline conformance fixtures, S2 retains isolated mapper/export evidence, S3 supplies the integrated one-controller uncertainty viewer, and S4 expands it to the match. The following are technical dependencies within those gates, not permission to skip stages.

1. **S1/S2: integrate evidence from the Pi authority.** The coordinator belongs to the physics repository: its proposed exchange retains all four raw timestamps and source/reference sessions, then publishes accepted immutable maps and fit/lifecycle evidence. Use offline fixtures at S1 and real isolated exports at S2. The exact fitter, fit window, outlier/asymmetry treatment and uncertainty-growth method need implementation and validation by their owner. Preserve local clocks and `T_pi = a * t_source + b`; debug is not the fitting authority.
2. **Preserve runtime mapping choices.** Export a map registry and Pi-issued association records identifying the exact version used for each source timestamp conversion. Raw source emitters do not need that ID or synchronous publication; a derived index joins immutable source events/samples to the runtime records. A shared batch retains a separate map binding for each converted source value. Retain raw events and missing-record counters asynchronously. A missing map/reference becomes an evidence gap, not a new gameplay failure or an excuse to use the latest fit. Preserve all historic maps and time-stamped lifecycle boundaries.
3. **S3: build the per-source state panel.** Show signed offset at a declared anchor, drift ppm, last-good-exchange age, uncertainty evaluated at the displayed time, reference epoch, map ID and text status/reason: `initializing`, `valid`, `uncertain`, `expired` or `invalid`. Apply the existing proposed 1 s refresh, 5 s expiry and 2 ms/source gate without claiming they have been achieved. Current expiry/reboot must not reclassify valid earlier history.
4. **S3: build bounded timelines and duration reports.** Use the runtime map for each event, show numeric uncertainty intervals and raw/mapped/map-ID/bound-component details. Join causal arrows by identities. Cross-source duration intervals conservatively sum mapping and capture bounds; overlapping intervals do not justify an exact total order. Invalid/unknown/expired map use stays in unsynchronized local lanes with identifier links and no cross-device duration value. Local RTT/electrical/marker metrics remain map-independent.
5. **Validate correctness before presentation claims.** Use known-answer fixtures for fixed positive/negative offsets, positive/negative drift, asymmetric exchange delay, outliers, noisy and over-limit fits, uncertainty growth, rejected updates, expiry and Pi/source reboot. Test missing map references, nearly crossing event intervals, observer source loss, valid historical events after current expiry, wrong-epoch reuse and preservation of raw times. Verify that 2 ms at both endpoints contributes 4 ms before capture error and that local metrics are unchanged. Add fitting/metadata/viewer tests only with their implementations; the current auditor tests do not cover these requirements.

Acceptance also requires measured hardware/software timestamp placement, network asymmetry and instrumentation overhead on the selected setup. A smooth aligned timeline or small fit residual is not proof of synchronization accuracy. The planned viewer must expose uncertainty and missing evidence throughout a run.

Include trace-only IRQ/render fixtures that use Pi-issued source-time selection intervals for a labeled `display_mapping`. Keep actual `runtime_mapping_use` references authoritative and do not repair a missing expected runtime reference with a display assignment. Test selection gaps/overlaps, immutable past assignments and Pi-native identity conversion with event-capture uncertainty. This display path must not require physics to receive the debug event stream.

## Doubles match trace work package

Define expected fixtures at S0, implement offline contract checks at S1 after the full-match schema is reviewed, and validate integrated four-player traces at S4. Follow the canonical [gameplay](https://github.com/motion-tennis/documentation/blob/main/docs/gameplay.md) and [assignment](https://github.com/motion-tennis/documentation/blob/main/docs/player-assignment.md) contracts. Preserve roster revision and one-to-one team/player/avatar/controller/person bindings; body-local gesture and automatic-avatar target/movement evidence; assigned-server lift/toss/stroke/attempt/fault/let transitions; and contact/bounce/out/point/score events linked to accepted commit identities. Technical faults remain distinct from sporting outcomes, and ordinary per-sample `MISS` results do not award points. The existing auditor does not validate these rules; this work package adds no wire types, code or schema and leaves 200 Hz traffic, marker behavior and clock-map evidence unchanged.

- Add deterministic fixtures for four unique roster bindings and the full-readiness barrier with no automatic AI filling; legal net-touch rallies, service lets, first/second faults, deuce, tiebreaks and serve/receiver order according to the shared rules. Verify that side/front-back-role changes never change team/player identity and that technical interruptions do not fabricate points.
- Check that duplicate updates cannot award a point twice, rejected commits roll back candidate ball/avatar/serve/score effects together, and each rule result references the correct committed state. Retain rejected/ambiguous paths and all ordinary sample outcomes rather than inferring score from controller `MISS` counts.
- Record viewport/team, camera side, render-frame and shared committed-version/presentation identities for the two views. Test consistent world/contact results, camera changes after end changes, and interpolation splits at contact/bounce/net/serve/point/reset boundaries. Rendering and debug analysis cannot become another scorer, movement controller or collision authority.

## Storage and process isolation

Each source uses a bounded ring and a lower-priority exporter. The collector uses separate receive, storage and view/update stages with finite queues and counters. Retain loss counts when storage or the viewer falls behind. Disk saturation must degrade observation, not block feedback. Use append-only per-source logs and a manifest; produce merged reports offline. Declare storage caps before enabling image/packet recording.

Raw live trace datagrams obey the central 1,200-byte limit. JSONL is the offline normalized representation, not the proposed high-rate wire encoding. Instrumentation verbosity, sampling of optional diagnostic payloads and raw-frame capture are run parameters. Never sample away started/terminal transaction accounting without preserving counters and explicitly marking the trace incomplete.

## Experiments within shared gates

The [workflow table](workflow.md#stage-responsibilities) is the stage mapping for these experiments. Run existing audit/tests for relevant S0 contract work; add isolated conformance fixtures at S1. At S2 collect bounded component/transport probes and compare local counters with available packet/GPIO evidence. S2 feasibility evidence does not constitute a full game.

At S3 demonstrate one real controller's complete marker/sample/query/commit/feedback path, numeric Pi-time uncertainty and diagnostic replay with real outcome/evidence gaps. At S4 expand to four confirmed humans, full doubles rules/association and both team views. Synthetic one-to-four-source load probes may support earlier isolated feasibility tasks, but they never establish four-player match readiness.

S5 runs the matched workload/fault matrix: one through four controllers, valid hits/misses, occlusion/crossings, stale inputs/state, simultaneous inputs, CPU/render load, network delay/jitter/loss/duplicates/reordering, queue overflow and service restarts. Preserve full denominators and distinguish the one-to-three-controller diagnostic workloads from a four-player match. Measure the 5 ms batching, 30 ms response p99, 40 ms eligible-feedback p99 and 50 ms expiry targets without claiming guarantees. Include marker failures/unresolved paths, haptic-induced triggers and externally checked instrumentation overhead. Archive original evidence and seeds. S6 requires reproducibility by another contributor; S7 alternatives remain deferred without explicit scope.

The S5 [WLAN A/B comparison](https://github.com/motion-tennis/documentation/blob/main/docs/networking.md#external-ap-versus-pi-hotspot-comparison) retains Wi-Fi and compares an external AP against a Pi-hosted hotspot, with a wired laptop in both. Run three 10-minute baselines at each controller count per variant with matched load/fault cases. Preserve the 200 Hz traffic, application protocol, deadlines, marker configuration and telemetry level. Record `network_variant`, addresses/interfaces, bridge/routing configuration, run order and radio/load conditions in each manifest. Verify controller-to-Windows UDP 41030 reachability before collection; capture on the correct Pi WLAN/Ethernet/bridge interfaces without double-counting packets. Reports must separate each variant's complete response/electrical and marker populations, failures, Pi load and recovery. No live A/B runner or results exist yet; ESP-NOW is outside this work package. Earlier S2 reachability probes establish feasibility only and do not replace matched S5 evidence.
