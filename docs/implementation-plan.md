# Runtime debug environment implementation plan

[Repository home](../README.md) · [Trace contract](trace-format.md) · [Central debug specification](https://github.com/motion-tennis/documentation/blob/main/docs/debugging.md)

Only the offline auditor and its fixtures/tests exist. The modules below are planned entry points, not executable names or available commands. Implement them in this order and update the README with real commands when they exist.

| Deliverable | Host and responsibility | Acceptance evidence |
| --- | --- | --- |
| Source trace adapters | ESP32 firmware, Pi physics, Windows tracking/game; compact preallocated records at actual event boundaries, including additional IMU threshold IRQ markers | Bounded writes; original source clocks preserved; measured overhead; every started request and captured marker represented or loss counted; unchanged 200 Hz gameplay stream |
| Collector | Separate Windows Python process; bounded UDP trace-batch receiver on reference port 41030 | Protocol/version checks, source registry, event-sequence tracking, bounded queues, asynchronous JSONL writing, retained Pi map/exchange/use records, no blocking of gameplay |
| Run controller | Windows operator API, reference TCP 41043; builds manifests and starts/stops only explicitly selected test runs | Records exact revisions/profiles/hardware, seeds, source readiness, clock mappings and output paths; never starts network fault injection implicitly |
| Packet decoder | Wireshark/TShark-compatible analysis of the canonical gameplay wire envelope | Identifies controller/session/request, batch/query/update, message type and state version from fixtures; reports undecodable/version-mismatched packets |
| Timeline viewer | Local Windows UI reading collector output or completed bundles | Four controller lanes, per-transaction waterfall, selectable IMU markers linked through pose/query/decision/commit/feedback; Pi-reference map state panel, numeric error intervals and explicit gaps/failures; paused viewer cannot block collection |
| Simulators and stubs | Desktop test processes emulating four controllers, tracking frames and game snapshot/commit service | Deterministic seeds; preserved per-transaction query/response even in batches; hit/miss/invalid/timeout/duplicate cases |
| Replay/fault harness | Test-only transport adapters; explicit opt-in execution | Seeded delay/jitter/loss/duplicate/reorder/corruption/restart per message boundary; fault log distinguishes injection from native loss |
| Protocol-aware auditor | Offline extension of the local auditor | Detects missing logical ball queries, uncommitted positive feedback, duplicate state application, old epochs, false freshness and incomplete source manifests; validates marker provenance/links, Pi map references and event-time validity; reports separate marker populations and conservative cross-clock intervals |
| Hardware trace import | Offline logic-analyzer/photodiode/vibration traces joined using calibrated markers | Known units and clock transforms, declared thresholds and uncertainty, no inference of physical output from software alone |

Python is the reference orchestration/analysis language. Critical emitters use each component's implementation language and do not depend on Python in interrupt/tick paths. The viewer technology and pinned tool versions must be selected and recorded with the first runtime implementation; an initial offline HTML timeline is sufficient if it exposes the required evidence. A database or cloud dashboard is not required for the first milestone.

## IMU marker integration work package

The user-confirmed direction adds a configurable hardware acceleration-threshold interrupt as a diagnostic marker while keeping the continuous gameplay stream unchanged. Implement the [marker trace contract](trace-format.md#additional-imu-threshold-markers) and [shared design](https://github.com/motion-tennis/documentation/blob/main/docs/imu-trigger-markers.md) in this order:

1. Characterize the selected IMU's detector semantics, supported threshold/duration/filter settings and evaluation rate independently of its raw sample ODR. Verify concurrent regular acquisition and threshold-IRQ delivery, hardware-edge/ISR timestamp error, interrupt clear/latch behavior, repeated triggers and haptic-induced motion. Record actual firmware/driver capabilities, including any required Zephyr driver extension; reading samples alone does not establish threshold-IRQ support.
2. Add bounded `imu_threshold_trigger` and `trigger_link` records. Preserve `t_trigger` on the ESP32 clock, configuration version, session-scoped identity and explicit primary sample/transaction link. Keep unresolved timing/association evidence visible; never change a failed target to a later successful sample.
3. Extend the collector/viewer to join the marker through existing transaction, pose, logical query, batch, decision, accepted commit, feedback and eligible cue identities. The marker remains debug metadata; do not modify the gameplay schema, 200 Hz schedule, queue priority or 50 ms transaction expiry.
4. Extend the offline auditor with meaningful marker fixtures and checks before claiming marker analysis works. Cover wrong sessions, reboot, ambiguous capture timing, missing/duplicate links, several markers per transaction, dropped/failed targets, out-of-order records, missing stages and source loss. Preserve the supplied core transaction tests.
5. Publish separate ordinary sample, primary marker-response and explicitly linked semantic swing/cue measurements. Count all marker outcomes and report observation cutoffs, uncertainty and detector delay. Compare marker instrumentation enabled/disabled under identical stream load; log collection must not become a gameplay dependency.

Only the existing core offline auditor is implemented. Its acceptance of additional named stage records does not satisfy this work package or establish full-path marker tracing.

## Clock-mapping and uncertainty-viewer work package

The agreed design uses Pi-owned affine mappings with drift correction and visibly bounded debug timing. Follow the [metadata contract](trace-format.md#pi-reference-clock-metadata), [canonical clock mapping](https://github.com/motion-tennis/documentation/blob/main/docs/coordinates-and-time.md#pi-reference-clock-mapping) and [ADR 0009](https://github.com/motion-tennis/documentation/blob/main/docs/adr/0009-pi-reference-clock-mapping.md). This work does not change the gameplay protocol, profile rates or deadlines.

1. **Implement the Pi authority and evidence export.** The proposed coordinator initiates the existing TCP exchange, retains all four raw timestamps and source/reference sessions, then publishes accepted immutable map versions and fit/lifecycle evidence. The exact fitter, fit window, outlier/asymmetry treatment and uncertainty-growth method need implementation and validation. Preserve local clocks and use `T_pi = a * t_source + b`; the collector is not the fitting authority.
2. **Preserve runtime mapping choices.** Export a map registry and Pi-issued association records identifying the exact version used for each source timestamp conversion. Raw source emitters do not need that ID or synchronous publication; a derived index joins immutable source events/samples to the runtime records. A shared batch retains a separate map binding for each converted source value. Retain raw events and missing-record counters asynchronously. A missing map/reference becomes an evidence gap, not a new gameplay failure or an excuse to use the latest fit. Preserve all historic maps and time-stamped lifecycle boundaries.
3. **Build the per-source state panel.** Show signed offset at a declared anchor, drift ppm, last-good-exchange age, uncertainty evaluated at the displayed time, reference epoch, map ID and text status/reason: `initializing`, `valid`, `uncertain`, `expired` or `invalid`. Apply the existing proposed 1 s refresh, 5 s expiry and 2 ms/source gate without claiming they have been achieved. Current expiry/reboot must not reclassify valid earlier history.
4. **Build bounded timelines and duration reports.** Use the runtime map for each event, show numeric uncertainty intervals and raw/mapped/map-ID/bound-component details. Join causal arrows by identities. Cross-source duration intervals conservatively sum mapping and capture bounds; overlapping intervals do not justify an exact total order. Invalid/unknown/expired map use stays in unsynchronized local lanes with identifier links and no cross-device duration value. Local RTT/electrical/marker metrics remain map-independent.
5. **Validate correctness before presentation claims.** Use known-answer fixtures for fixed positive/negative offsets, positive/negative drift, asymmetric exchange delay, outliers, noisy and over-limit fits, uncertainty growth, rejected updates, expiry and Pi/source reboot. Test missing map references, nearly crossing event intervals, observer source loss, valid historical events after current expiry, wrong-epoch reuse and preservation of raw times. Verify that 2 ms at both endpoints contributes 4 ms before capture error and that local metrics are unchanged. Add fitting/metadata/viewer tests only with their implementations; the current auditor tests do not cover these requirements.

Acceptance also requires measured hardware/software timestamp placement, network asymmetry and instrumentation overhead on the selected setup. A smooth aligned timeline or small fit residual is not proof of synchronization accuracy. The planned viewer must expose uncertainty and missing evidence throughout a run.

Include trace-only IRQ/render fixtures that use Pi-issued source-time selection intervals for a labeled `display_mapping`. Keep actual `runtime_mapping_use` references authoritative and do not repair a missing expected runtime reference with a display assignment. Test selection gaps/overlaps, immutable past assignments and Pi-native identity conversion with event-capture uncertainty. This display path must not require physics to receive the debug event stream.

## Doubles match trace work package

Implement trace coverage against the canonical [gameplay](https://github.com/motion-tennis/documentation/blob/main/docs/gameplay.md) and [assignment](https://github.com/motion-tennis/documentation/blob/main/docs/player-assignment.md) contracts after the full-match schema is reviewed. Preserve roster revision and one-to-one team/player/avatar/controller/person bindings; body-local gesture and automatic-avatar target/movement evidence; assigned-server lift/toss/stroke/attempt/fault/let transitions; and contact/bounce/out/point/score events linked to accepted commit identities. Technical faults remain distinct from sporting outcomes, and ordinary per-sample `MISS` results do not award points. The existing auditor does not validate these rules; this work package adds no wire types, code or schema and leaves 200 Hz traffic, marker behavior and clock-map evidence unchanged.

- Add deterministic fixtures for four unique roster bindings and the full-readiness barrier with no automatic AI filling; legal net-touch rallies, service lets, first/second faults, deuce, tiebreaks and serve/receiver order according to the shared rules. Verify that side/front-back-role changes never change team/player identity and that technical interruptions do not fabricate points.
- Check that duplicate updates cannot award a point twice, rejected commits roll back candidate ball/avatar/serve/score effects together, and each rule result references the correct committed state. Retain rejected/ambiguous paths and all ordinary sample outcomes rather than inferring score from controller `MISS` counts.
- Record viewport/team, camera side, render-frame and shared committed-version/presentation identities for the two views. Test consistent world/contact results, camera changes after end changes, and interpolation splits at contact/bounce/net/serve/point/reset boundaries. Rendering and debug analysis cannot become another scorer, movement controller or collision authority.

## Storage and process isolation

Each source uses a bounded ring and a lower-priority exporter. The collector uses separate receive, storage and view/update stages with finite queues and counters. Retain loss counts when storage or the viewer falls behind. Disk saturation must degrade observation, not block feedback. Use append-only per-source logs and a manifest; produce merged reports offline. Declare storage caps before enabling image/packet recording.

Raw live trace datagrams obey the central 1,200-byte limit. JSONL is the offline normalized representation, not the proposed high-rate wire encoding. Instrumentation verbosity, sampling of optional diagnostic payloads and raw-frame capture are run parameters. Never sample away started/terminal transaction accounting without preserving counters and explicitly marking the trace incomplete.

## Controlled experiment sequence

1. Run the supplied synthetic audit and integrity tests.
2. Add source emitters and collector; compare one controller's transaction/marker ledgers against local counters and GPIO traces. Verify the distinct regular sample IRQ and threshold-marker boundaries.
3. Run simulated input at the reference 200 Hz per controller, first one then four controllers; observe all 800 logical transactions per second and their batched state operations.
4. Inject loss/duplicate/timeout/conflict cases and verify that every attempt has a response or counted local failure.
5. Add real camera inference and render load on the Windows laptop; report their separate resource and latency effects.
6. Add real controllers and Pi 3B; measure rather than assume the 5 ms batching target, 30 ms response p99, 40 ms eligible-feedback p99 and 50 ms expiry behavior.
7. Trace selected threshold markers across the complete path, including failed and unresolved markers, and test haptic-induced/repeated triggers. Compare instrumentation levels using external timing markers and an unchanged gameplay stream. Archive the full run evidence before accepting a performance claim.

The first full acceptance run must exercise one through four players, valid hits/misses, occlusion and identity crossings, stale frames/ball snapshots, simultaneous inputs, CPU/render load, network delay/jitter/loss/duplicates/reordering, queue overflow and every service restart. Retain completion distributions alongside timeouts, invalid tracking, admission drops, target exceedances and logging loss. Hardware/driver/runtime limits remain empirical until a bounded platform and workload have been verified.

The planned [WLAN A/B comparison](https://github.com/motion-tennis/documentation/blob/main/docs/networking.md#external-ap-versus-pi-hotspot-comparison) retains Wi-Fi and compares an external AP against a Pi-hosted hotspot, with a wired laptop in both. Run three 10-minute baselines at each controller count per variant with matched load/fault cases. Preserve the 200 Hz traffic, application protocol, deadlines, marker configuration and telemetry level. Record `network_variant`, addresses/interfaces, bridge/routing configuration, run order and radio/load conditions in each manifest. Verify controller-to-Windows UDP 41030 reachability before collection; capture on the correct Pi WLAN/Ethernet/bridge interfaces without double-counting packets. Reports must separate each variant's complete response/electrical and marker populations, failures, Pi load and recovery. No live A/B runner or results exist yet; ESP-NOW is outside this work package.
